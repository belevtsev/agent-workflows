# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

This is the v3.0.0 breaking change: the v2 installer is removed, and Claude Code
and Codex get the skills from plugins. v2 users clean up the v2 installation by
hand before installing the plugins; see "Cleaning up a v2 installation" in
`docs/operations.md`.

### Breaking

- **Task records with test rules.** `cw task start` records `"test_rules": "go.test-evidence/v1"` in every new task record (the record `version` stays 3), so cw releases before this one cannot read task records it starts; an older cw's commit and push hook skips them (fails open). Finish such a task with this cw, or abandon it. Records without `test_rules` load and verify as before, and their results files and `cw task trace` reports are byte-identical. A handoff to such a record also stores `gofmt_sha256` on the changed Go test files of a contract-bearing result, and check results files store each test's `run` and `marked` counts.
- **Task records with check amendments.** `cw task add-checks` stores added checks in a new `amendments` member of the task record, so cw releases before this one cannot read a record it amends. An older cw's commit and push hook skips records it cannot read, so it does not gate them: upgrade every cw that runs the hooks. Records that are never amended are unchanged.
- **Task records with packs.** `cw task start` records the task's pack set in a new `packs` member, so cw releases before this one cannot read task records it starts. An older cw's commit and push hook skips records it cannot read, so it does not gate them: upgrade every cw that runs the hooks.
- **Stricter Go evidence rule by default.** The `go` pack now names `go.package-test/v2`, so new tasks in Go modules need, for each changed package, a passed direct `go test -race` run covering it (a plain run, with a limitation naming the reason, where `-race` cannot run on the host); for each package whose test binary links a changed package, a passed `go test` run covering it; and a passed `go test ./...` run after a change to `go.mod`, `go.sum`, `go.work`, `go.work.sum`, vendored files, build-constraint lines, generated code, embedded files or testdata outside any package, or when `go list` cannot compute the package graph within 5 s. Verify runs `go list -race runtime` and `go list -deps -test` offline (`GOPROXY=off`) inside the task lock, for at most 6 s. A pass after a failed run of the same check at the same source and `GOFLAGS` earns no credit, and skipped tests are listed as limitations (a run without `-v` or `-json` gets a limitation saying they could not be listed). Tasks already started keep the rule they recorded. `cw pack remove go` writes an explicit `packs.json`, which drops the Go rule for all of that user's repositories, leaving only the fallback rule (any passed check); `cw pack add go`, or deleting `packs.json`, restores it. There is no way back to `go.package-test/v1` for new tasks.
- **No v2 migration.** `cw migrate-v2` and all v2-to-v3 migration support are removed (`internal/v2migrate`, and `codexinstall.RemoveBlockFromFile`, which only the migration used); `cw migrate-v2` is now an unknown command (exit 2). v2 installations are cleaned up by hand: remove the links into the v2 state directory, move skills v2 adopted back out of `backups/personal-skills/`, remove the managed blocks in the Claude home's `CLAUDE.md` (`$CLAUDE_CONFIG_DIR`, else `~/.claude`) and `$CODEX_HOME/AGENTS.md`, and delete v2's `current`, `releases`, `bases`, `runtime`, `state.json`, `journal.json` and `mutation.lock`, keeping `workflow-tasks/`; see "Cleaning up a v2 installation" in `docs/operations.md`.
- **Agent roster.** The plugin ships seven agents, all under `agents/` and without the `cw-` prefix: `spec-writer`, `architect`, `implementer`, `test-engineer`, `reviewer`, `github-worker` and the opt-in `adversarial-tester` (see Added). `cw-test-author` is removed: `agent-workflows:test-engineer` is the one independent test author, and the rules of `references/test-author.md` (independence, the `cw task contract-extract` declaration extract, feedback limits, authorship apart from execution) now live only in `contracts/test-engineer.md`. `cw-reviewer` and `spec-reviewer` are replaced by `agent-workflows:reviewer` (`model: opus`, `effort: high`), whose brief names one of four contracts: `spec-review`, `design-review`, `test-review` or `code-review`. `cw-github-worker` becomes `agents/github-worker.md` (`model: sonnet`, `effort: medium`). `global/claude-agents/` and the `claude_agents` entry of `skills-manifest.json` are removed. Briefs and dispatches that name `agent-workflows:cw-reviewer`, `agent-workflows:cw-test-author`, `agent-workflows:cw-github-worker` or `agent-workflows:spec-reviewer` must switch to the new types. Policy roles: `spec_reviewer` and `testing` are replaced by `spec_review`, `design_review` and `test_review` (the test engineer keeps `test_engineer`). `cw metrics` reports a worker dispatched as `agent-workflows:test-engineer` (or as `cw-test-author` in older transcripts) under the `test_author` role label, and recognises the new and old reviewer and GitHub worker types; a test engineer dispatched as `general-purpose` is labelled `test_author` only when its description or brief says "test author", and otherwise by its brief's role.
- **Review loops at every stage.** The flow is spec-writer ⇄ reviewer (spec) → architect ⇄ reviewer (design) → implementer ∥ test-engineer ⇄ reviewer (tests, before integration and without the implementation) → integrate and run → reviewer (code) ⇄ implementer → `cw task verify` → gated commit. Findings go back to the stage's author; the severity grades and the review cap, now applied per stage, live once in `worker-handoffs.md` "Review stages". The design review checks the decision record and interface contract against the spec, sources and code; the test review checks that every requirement maps to a test that can fail for its defect (red-first or a mutant), and for flakiness and timing bounds that also limit real work. After the before checkpoint, which is unchanged, advisers join only at four decision points (open spec questions, the architect's design choice, rejecting a blocker or major finding, the final checkpoint) and only when the task binds any; otherwise each point is skipped and recorded as "no advisers configured". `cw task verify` is unchanged: with no bound advisers a required checkpoint already takes the offline `no_advisers_configured` record.
- **Archify is the only diagram tool.** The README embeds a static SVG exported by the vendored archify from `docs/diagrams/workflow-overview.json`; `docs/decision-flow.md` embeds `docs/diagrams/decision-flow.svg`; `docs/diagrams/validated-worker-handoffs.json` is removed as stale. Mermaid is gone from every first-party file, skills and contracts point to the `archify` skill for diagrams, and a skillcheck test fails on a first-party Markdown file with a mermaid code block. CONTRIBUTING has a "Diagrams" section with the regenerate commands.
- The Go module path is now `github.com/belevtsev/agent-workflows/v3`, so `go install …@latest` can resolve v3 release tags. The old install path without `/v3` (`go install …/agent-workflows/cmd/cw@…`) no longer gets updates: its `@main` and `@latest` queries fail with a module path mismatch; install with `go install github.com/belevtsev/agent-workflows/v3/cmd/cw@main` (or `@latest` once the first v3 tag exists). Code that imports `github.com/belevtsev/agent-workflows/...` must import `github.com/belevtsev/agent-workflows/v3/...`.

### Added

- `cw task authorship --task DIR` prints, as one JSON line and without changing the record, each Go test file changed since `cw task start` with its authorship status (`independent`, `source_aware`, `lost` or `unowned`), the reason, and the assignment, agent, contract and finding the status rests on, plus problems such as an unreadable baseline manifest. It works on an abandoned task and exits 0 whatever the statuses (1 when the task cannot be loaded, 2 on a usage error). See "Test rules and test authorship" in `worker-handoffs.md`.
- `cw task add-checks --task DIR --input FILE|- [--summary]` adds credited direct `go test` checks to a started substantial task after it merges its base branch with `git merge --no-ff <base>`. The input names the merge commit, the base ref, a reason and the checks. The plan stays byte-identical; added checks get new IDs, are never replaced, removed or narrowed, and each must cover a package or module file the merge changed that no earlier check covers. Git merge history is checked only at admission: the merge commit must be reachable from HEAD and not from the task baseline or the base, with a parent after the first reachable from the base, in a repository that is not shallow. An accepted amendment clears the stored verification; added checks then run, bind and earn verify credit like plan checks. See "Merging the base branch during a task" in `docs/operations.md`.
- `cwdev diagram-svg` exports an archify spec to the SVG that the viewer's **Export → SVG · Auto** button downloads, in one command: `go run ./cmd/cwdev diagram-svg --all` regenerates every `docs/diagrams/*.svg`, `cwdev diagram-svg SPEC.json [--out FILE]` exports one spec, and `--check` writes nothing and fails when a committed SVG differs from a fresh export. It runs archify `finalize`, then clicks the viewer's own export item in headless Chrome (found like archify's `findChrome`, including `ARCHIFY_CHROME`), driven over the DevTools pipe with no new Go dependency, and captures the downloaded blob. Output is byte-identical across runs on one machine and the committed SVGs already match it; `--check` is not in CI because byte equality across operating systems and Chrome versions is unproven. It needs node and Chrome, and fails without writing when either is missing, finalize fails, the export is empty or invalid, or `--timeout` expires.
- Pack manifests: the built-in Go pack `packs/go/pack.yaml` (schema 1, `kind: language`), embedded in `cw` and checked by `internal/skillcheck`.
- `cw pack list|add|remove` (alias `cw lang`) and `packs.json`, the pack selection in the configuration directory.
- **Cost history.** `cw metrics import ... --append [--history FILE]` appends one JSONL record per de-duplicated request (token counts, session and request ids, agent id, role and type, model, timestamps; no prompt text, tool data or file contents) to `metrics/history.jsonl` under the state directory, so cost data survives transcript cleanup. Records are keyed by `(source, session_id, request_id)`: re-importing a session, or importing it after it grew, never double-counts, and a stored record with different counts is kept and reported as `conflicting`. Writers take an exclusive `flock` on `<history>.lock` and append whole lines in one write; a new history is created 0600 in a 0700 directory, symlinks are refused, and the file is capped at 1 GiB. `cw metrics history [--session ID] [--model M] [--since DATE] [--until DATE] [--prices FILE]` aggregates it by model, UTC day and session, recomputes dollars from the price table you pass, and reports damaged lines instead of dropping them. See "Cost history" in `docs/operations.md`.
- Four eval cases. `reviewer/spec-claude-md-probe` and `test-engineer/clamp-claude-md-probe` (tag `instruction-probe`) plant a unique `MARKER_` string in the workspace `CLAUDE.md`, ask the agent to list every marker in its context, and fail when the marker reaches the trace, the agent's artefact or the brief, or when the agent opens a `CLAUDE.md` or `AGENTS.md`. `claude plugin eval` disables CLAUDE.md loading for every run (`CLAUDE_CODE_DISABLE_CLAUDE_MDS=1`), so inside the runner they catch only a marker that arrives by another path; `evals/README.md` "Instruction-file probe" gives the ordinary-session commands that measure `omitClaudeMd` itself. `reviewer/design-revision-scope-growth` is a follow-up design review whose revision resolves the accepted findings and slips in an unrequested per-endpoint circuit breaker, which must be flagged as `scope creep`. `architect/ledger-money-adr` works in a repository with `docs/decisions/` and checks the ADR the architect writes there. The reviewer suite now has nine cases and the architect and test-engineer suites four; the eval job timeout rises to 300 minutes.
- `cw publish --task DIR --message-file FILE --expect-head SHA --push REMOTE --branch BRANCH` commits a verified task's files (its change set since `cw task start`, or the `--path` values in it, whole files only), pushes the commit to `refs/heads/BRANCH` of REMOTE and, with `--pr create` or `--pr edit` (`--repo`, `--base`, `--title`, `--body-file`), creates or edits the pull request through `gh`. It runs only after `cw task verify` passed on the current source and no other open task record gates the repository (the gate of `cw hook pre-publish`, applied by the command itself, so Codex gets it too), reads back every step, never amends, force-pushes or pushes tags, and continues from the observed state when the same command runs again. Exit statuses: 0 published, 1 failed, 2 usage, 3 denied, 4 refused, 5 unknown, 6 mismatch, 130 cancelled, each with a stable reason. Each run appends a hash-chained `started` and `finished` entry (`publication-NNNNNN.json`) to the task directory, under a `.publish-lock`; task revisions are never touched. The coordinator runs it under the user's authorization: cw authorizes nothing. Requires Git 2.24 or newer.
- Opt-in adversarial white-box tester: `agents/adversarial-tester.md` (`model: opus`, `effort: high`) and `contracts/adversarial-tester.md`. A plan opts in at classify, before `cw task start`, when the change touches concurrency, parsing or untrusted input, security or data integrity, or when the user asks; it then holds a requirement naming the opted-in areas and a check that writes a coverage profile outside the source tree. The tester reads `interface-contract.md`, `design.md`, the integrated source and the coverage profile, and runs on the same source as code review, in parallel with it, as an `evidence` assignment that never changes source. Every test it keeps must fail on the current implementation (in each of three runs) and cite the requirement ID or design rule it shows broken; passing probes are discarded. Each kept test is a severity-graded finding with the command that runs it, for the implementer; after the fix it stays as a regression test written with source access, recorded the way `code-review.md` records a reviewer's reproduction test (the acceptance's `check_ids` cite a passing run of it, the disposition's `evidence` names the test and its `reason` says the adversarial tester wrote it with source access; `test-strategy` and `code-review.md` name the tester as the one other source-aware exception), and never counts as black-box coverage. Nothing it produces reaches the test engineer except a requirement ID the coordinator chooses to send. Policy role `adversarial_tester` on both hosts. Eval suite `evals/adversarial-tester/` with three cases (concurrency, parsing, security), each seeding a defect in internal code that the contract-level tests miss. `TestAdversarialGate` runs an eval run's kept tests alone on each case's seeded source (each must fail) and the whole package after the case's `fix.patch` (it must pass); the evals workflow runs it for the `adversarial-tester` suite, and `TestAdversarialFixtures` checks the patches offline.
- Eval suites are checked in CI and run on a schedule: `go test ./evals/...` validates every case's files, grader regexes, graded paths and dispatched agents offline; `.github/workflows/evals.yml` runs each suite weekly or on demand with a default ceiling of 5 dollars per three cases and a 0.8 pass floor when `ANTHROPIC_API_KEY` is set; and a mutant gate fails a test-engineer run whose authored tests pass with any of the case's `testdata/impl-mutants/*.patch` applied. See `evals/README.md`.
- The spec-writer agent under `agents/` and the spec-writer and spec-review contracts, which write and review OpenSpec-compatible change folders (`openspec/changes/<change-id>/` with `proposal.md`, spec deltas and `tasks.md`), the policy roles `spec_writer` and `spec_review`, eval suites under `evals/`, and the flow in `skills/task-orchestration/SKILL.md` and `references/contracts/README.md` (see "Review loops at every stage" above).
- `cw task timeline --task DIR [--summary]` reports, read-only, the wall time of each worker assignment (assignment to handoff, handoff to acceptance) and each check run, and the task's elapsed time from `created_at` to its last stored revision (`updated_at`), from timestamps the record already stores; a timestamp the record does not hold, and every duration computed from one, is `n/a`. `--summary` prints JSON Lines: one compact object for the task, then one per entry. See "Global project diagnostics and evidence" in `docs/operations.md`.

- Requirement traceability in `cw task`. A worker brief may carry `inputs` (up to 32 artefacts, each with its SHA-256), which `assign` checks and stores as private copies that `verify` re-checks. A test engineer's brief declares `requirements` (each contract requirement with the plan requirements it implements), and its completed handoff carries a `requirement_map` naming, for each requirement, the Go tests in files a test-engineer round changed, or an `uncovered` reason. Every check run records the per-test results of the `-json` events in its complete output as `test_results`; `verify` fails a mapped test that is missing, failed, only skipped or has no PASS in a latest passed run of a per-test-credited `go test -json` check at the current source, and a plan requirement that lost every linking round. `cw task trace --task DIR [--summary]` reports each plan requirement with its contract requirements, mapped tests and the runs that recorded them, without changing the record. `cw task run --summary` takes `failing_tests` from a run's results when it has them. `assign` now requires `requirements` on a brief with a `contract` when the plan has a `go test` check whose argv earns per-test credit (`-json` in its own argv and only allowed flags), and refuses them when it has none; records made before this change still load, hash and verify as before, but compatibility runs one way: a record that gains any of the new members (`inputs`, `input_files`, `requirements`, `requirement_map`, `test_results`) can be read only by this `cw` or a later one, and an older `cw`, including an older `cw hook pre-publish`, fails to load it (so the old hook's commit gate fails open); update every installed `cw` before running tasks with this one. With go1.27.3 a line a test writes straight to stdout or stderr starting with byte 0x16 can forge a `-json` PASS, but cannot hide a real FAIL of the same test.

### Changed

- **Proven PASS, test authorship and contract currency (records with test rules).** Each check run's results also count, per test, its `run` events and its output lines beginning with byte 0x16. `cw task verify` and `cw task trace` count a mapped test as `passed` only when a per-test credited current passed run recorded at least one `run` event per result, no more `run` events than its `-count` times its `-cpu` values times the packages of the test's directory that declare it, and no marked line; otherwise the test is `pass_unproven`. This is a mitigation, not a proof: code in the test binary can still print a forged `=== RUN` and `--- PASS` pair, or unmarked framing before the first test, for a mapped test that never genuinely runs (a subtest never created, a build-constrained file, `os.Exit` before `m.Run`), and a same-named declaration in another package of the directory that does not run the mapped name raises the allowance; code review is the backstop (`contracts/code-review.md`). In a substantial task, every Go test file changed since start must be written by a never-rejected test-engineer round with a `completed` result whose latest acceptance is `accepted` or `unused` and whose agent is not the coordinator, held no implementation assignment without a contract and no review or verification assignment, and wrote in contract-bearing rounds only `_test.go` files and `testdata` paths (`independent`, also when only gofmt-formatted since), or be a reproduction test cited by a resolved finding in an acceptance that lists a check (`source_aware`); `verify` fails `lost` and `unowned` files, a mapped test whose file is not `independent` becomes `not_independent`, a plan without a per-test credited `go test -json` check fails once when a changed test file is not `source_aware`, an unreadable baseline manifest fails with `test authorship cannot be judged: ...`, and a selected path without `go.mod` gets a limitation. `cw task assign` refuses a brief with a `contract` in a substantial task whose plan cannot prove tests. An earlier contract is no longer re-extracted only when a later covering round has an `accepted` acceptance and no `rejected` one.
- The Go evidence rule now comes from the `go` pack (rule `go.package-test/v2`, see Breaking; tasks that recorded `go.package-test/v1` keep it). That pack is selected by default, when `packs.json` is absent, and is recorded by tasks that start with `go.mod` or `go.work` at the top of the selected path; its rule then checks packages whenever `go.mod` is at the top at verify. `cw pack remove go` writes an explicit `packs.json`; that drops the Go rule for all of that user's repositories, leaving only the fallback rule (any passed check); `cw pack add go`, or deleting `packs.json`, restores it. Pack detection is fixed when the task starts: a task that started with neither file gets no Go rule, even if it creates `go.mod` later, unlike tasks recorded by earlier releases, which still get it from `go.mod` at verify. `cw pack add` and `cw pack remove` affect only tasks started afterwards; an open task keeps the pack set it recorded.
- **Round budget per task.** A task allows at most two revision rounds of its spec, and at most two of its design and interface contract together, including contract amendments (the first spec, design and contract are not revisions), and at most two test-engineer rounds, the first dispatch and every return of a test that contradicts the contract included; implementer fixes and reviews never count, and neither do an exposure replacement or a correction round that `cw task verify` requires because source changed a declaration outside an amendment. When a finding or question would need a third round, the coordinator has the implementer fix what needs no counted round, keeps every other `blocker` and `major` open as `accepted` (never `deferred`), and asks the user whether to spend another round; the task stays open and nothing is published until those findings are resolved or rejected against evidence (`worker-handoffs.md` "Review stages").
- **Coverage-guided code review against the contract and the design.** The `code-review` contract now takes `interface-contract.md`, `design.md` and the coverage profile of the final check run as inputs. Every changed block the profile shows as unexecuted gets exactly one class: an untested requirement (a test finding, at least `major`, sent to a fresh test engineer as the requirement ID, contract-level inputs and expected outcome only, never lines, function names or profile data), unrequested behaviour (an implementation finding or a contract question), or an unreachable defence (`minor`). The quality bar adds design conformance (ownership, lifecycle and failure behaviour at each boundary `design.md` names) and names panics and goroutine or resource leaks. Every behaviour finding now carries a minimal test that fails on the current source, written in a scratch copy, and the command that runs it; a reviewer test that passes is discarded. The coordinator applies the test unchanged, accepts the fix only when a recorded check run of it passes, and records it as authored with source access: it stays as a regression test and never counts as black-box requirement coverage or replaces the test engineer's suite. There is no coverage threshold and no new gate, and the test engineer still never sees coverage. `global-workflow.md` shows a Go check with `-covermode=atomic -coverpkg=./... -coverprofile=<path outside the source>` (a profile inside the tree changes the source during the run, which `cw task run` records as `source_changed`); those flags already earn Go evidence credit. agent-workflows' own full check stays without coverage, because the `internal/graphify` process tests fail under `-cover`; a second check on the changed packages supplies the profile. `test-strategy` and `docs/workflow.md` exempt a reviewer's reproduction test from the fresh-test-engineer dispatch. Three `evals/reviewer/code-*` cases plant an untested requirement branch, an unrequested fallback and a design drift, each with its own grader, and `code-upload-quota` also plants a behaviour defect whose grader needs a failing reproduction; the `reviewer` suite's CI job timeout rises to 360 minutes, the GitHub-hosted maximum, for its twelve cases, and CI also keeps the `code-*` workspaces. The README roster and diagram, the contracts overview (with the contract-amendment procedure now open to a question a code-review finding raises) and the `docs/agents.md` design-choices FAQ name the new inputs; the FAQ no longer lists the internal-branch gap as open.
- **Reviewer and test engineer start without CLAUDE.md.** `agents/reviewer.md` and `agents/test-engineer.md` set `omitClaudeMd: true` (Claude Code 2.1.271 or newer; supported in plugin agents), so the user, project and local CLAUDE.md files no longer reach an independent review or test; managed policy files still load. The spec-review, design-review, test-review and test-engineer contracts now quote the Code Review Rules and working conventions each role applies, briefs quote any other project constraint (`worker-handoffs.md` "Brief and dispatch"), and both agents are told not to open `CLAUDE.md`, `CLAUDE.local.md` or `AGENTS.md` (the reviewer may when the change under review edits one). A skillcheck test (A5) fails when either agent drops the field or another agent sets it. The isolation holds on Claude Code only: Codex injects `$CODEX_HOME/AGENTS.md` and the project `AGENTS.md` into spawned agents (google/elephant-goldfish-model#237), as `hosts.md` now says.
- **Growth check on re-reviews.** When a spec or design is reviewed again after a revision, including the scoped design review of a contract amendment, the reviewer also flags, as `scope creep`, anything the revision added that no accepted finding asked for, apart from what the smallest fix of an accepted finding cannot do without; a user's answer to an open question and a question forwarded in an amendment count as accepted findings here (`worker-handoffs.md` "Review stages", referenced from the spec-review and design-review contracts).
- **Opt-in decision records.** When the architect chooses between real options in a way that is costly to reverse and the target repository keeps ADRs (`docs/decisions/` or an existing ADR folder), it also writes an ADR there in the `software-architecture` decision-record format, with any diagram drawn with archify; the flow names that folder among the architect's owned paths, the design review checks the ADR against `design.md` (new category `decision record`), and the ADR is committed with the change. A repository without such a folder gets no ADR. This repository keeps none.
- **Publication through `cw publish`.** `cw task start` refuses a plan with a check that runs `cw publish` (after cw's global flags), and `cw task run` refuses such a check in a recorded plan, with "publication and deployment commands are outside task checks"; this is a guard, not a sandbox. The coordinator now drafts the commit message and PR text and publishes a verified task with `cw publish`; `agent-workflows:github-worker` remains the fallback for hunk-level scopes, fork pull requests, split remotes, content conversions, message-rewriting hooks, records without a baseline manifest and repairing a mismatch (`references/github-worker.md`, `SKILL.md`, `worker-handoffs.md`, `global-workflow.md`, `contracts/README.md`, `docs/operations.md`, `docs/hooks.md`).
- **Latency rules and contract amendment.** `contracts/README.md` now says that test review starts as soon as the test engineer's handoff is recorded and overlaps the implementer, and that the coordinator asks the user the spec's or the architect's open questions while that stage's review runs; a spec question left to a choice still waits for bound advisers at point a. The reviewer sees the answers only in the follow-up review, as dispositions and the diff, and a revision that answers them always gets that follow-up. A new "Contract amendment" section gives the one path for a contract a downstream worker finds wrong. The coordinator batches the implementer's and test engineer's requirement-ID questions, stripped of either worker's work. The original architect, continued and given a separate checkout of the source the design was read from, revises the contract and writes `change-log.md`. A fresh reviewer re-binds the design review scoped to the changed requirements, under a review cap of its own per amendment. The coordinator re-hashes the contract, has the implementer put the amended declarations into source and nothing else, extracts the Go declarations again with `cw task contract-extract` (an extract carrying implementer-written detail is not sent), and refreshes both workers' assignments under new IDs, while unaffected cases keep moving. Workers never receive the change log or `design.md`. The architect, design-review, implementer and test-engineer contracts point to it. `worker-handoffs.md` lists the existing review fast paths in one place, with no change in meaning.
- **Checkpoint reasons cannot deny bound advisers.** `cw task start` refuses a plan whose `"required": false` checkpoint reason claims no advisers are configured, bound or available, or no adviser credentials are present, while the task binds any; the message names the bound IDs. Detection is a closed phrase heuristic with known false negatives and false positives (a reason about the task's own subject that matches must be reworded). `cw task verify` reports the same contradiction as a problem on every record it accepts, including those created earlier or by an older `cw`, unless both checkpoints are attached, and says whether to attach the final checkpoint, attach both or abandon and restart, or, when the source changed without a usable before checkpoint, stop and ask the user. A verification stored earlier is not re-evaluated until `cw task verify` runs again, and an older `cw` still creates such records until it is upgraded. The `cw doctor` credential details now name the environment they count: `credentials_launcher` and `credentials_codex_shell` say they are not `cw`'s own, `credentials_environment` says saved keys are not counted, and each points to `cw keys status`.
- `cw task start` refuses a substantial plan without a check bound to a requirement. `cw task verify` on a changed substantial task needs the latest run of some check passed at the current source and, when the task applies the `go` pack (see the Go pack entry above), a passed direct `go test` run whose `./...`, `./pkg` or `./dir/...` pattern covers each changed package (any file in its directory or `testdata/`; a non-Go file in a directory without Go files belongs to the nearest ancestor package); a changed `go.mod`, `go.sum`, `go.work` or `go.work.sum` needs `./...`. A run earns credit only when every flag in its argv and its `GOFLAGS` (split like cmd/go, recorded with compiler and linker flag values redacted) is on an allowlist of flags that cannot skip or replace tests, with `-count` at least 1 and a `test.` prefix only on flags go test passes to the test binary; `-run`, `-skip`, `-args`, `-c`, `-n`, `-exec`, `-toolexec`, `-overlay`, `-ldflags`, `-gcflags`, `-asmflags`, `-C`, unknown flags, a pattern after a flag that follows a pattern (`go test ./a -v ./b` tests only `./a`), wrappers (`make`, scripts), `GO.EXE` and Windows-style `.\pkg` patterns earn none. A check's argv is stored verbatim, so keep secrets out of it. The rules live in the language-neutral registry `internal/langpack`, with Go as its first pack. Open substantial tasks whose plan has no checks, or, in a Go module, whose checks run tests only through wrappers or with flags off the allowlist, cannot meet this: add a direct `go test` check and restart them.
- Worker findings carry `severity` (`blocker`, `major` or `minor`), required in review handoffs; findings recorded earlier read as `major`. `cw task verify` lists every rejected blocker or major finding as a limitation (first, as `rejected_findings`, with `--summary`), and a rejected blocker is a problem until a later accepted independent review, whose bundle lists the rejection, completes without re-raising it.

### Fixed

- The README roster no longer says the reviewer never sees the code. Code review reads the integrated source and its changed files and checks them against the requirements; only test review never sees the implementation. A note under the roster says that each stage's findings go back to its own author, that the implementer and test engineer run in parallel, and that small tasks skip the stages. The workflow diagram's code-review node now reads "code review: source + changes vs requirements", and `docs/agents.md` has a new "Design choices" section on common alternatives: merging the spec writer and architect, a test engineer that sees the code, implementer-written tests, cheaper models, a shell-script GitHub worker, and design and test review in parallel.
- Source capture no longer treats a Git repository as a plain folder ("Git identity is unavailable") or drops HEAD or the branch when a Git inspection command does not finish cleanly. Only Git exiting with a failure status, or no `git` on `PATH`, still means the path is not a repository. Any other end of any probe stops capture with one of: `Git inspection timed out after <budget> (git <probe>)`; `Git inspection was killed before it finished (git <probe>)` (detected on Unix); `Git inspection stopped by the caller (git <probe>): <reason>`; `Git inspection could not complete (git <probe>): <cause>`, which covers an unclean finish such as a child process holding Git's output open after Git exited. Each probe now has 60 seconds, still bounded by the caller's deadline, and 10 seconds instead of 100 milliseconds for its output after Git exits: on loaded machines 5 seconds was exceeded, failing `cw task start`, and 100 milliseconds was too short to copy a large listing. `cw hook pre-publish` bounds its Git and source-capture work with a 20 second deadline; a record whose source identity cannot be captured in time is skipped, as when capture fails, while other records can still gate. After a check runs, its source capture gets at most 20 of the 30 seconds for recording the result, so the result is still written when that capture fails or runs out, unless the task lock stays held through the remaining time; a check that passed but whose capture failed or ran out is recorded as `source_changed`.
- The commit gate stays shut while any open substantial record for the repository lacks a passing `cw task verify`; a newer record no longer hides an older open one, and the deny reason names every gating record with its verify and abandon commands. A verified record is finished, and stops gating, once another open substantial record starts, after that verification, from exactly the bytes it was verified on.
- The commit gate ages records by their latest revision instead of their start, so a task worked on for more than 14 days keeps gating.
- From a linked worktree of a record's checkout, the commit gate compares the linked worktree's source with the verified digest instead of the main checkout's.
- The commit gate's hook runs for every Bash command that names git (`Bash(*git*)`) and recognises `git -C DIR`, `command [-p] git`, `env [options] git` (following `env -C DIR`), `sudo`, `timeout`/`nice`/`stdbuf` wrappers, `$(...)` and backtick substitutions (checked from the directory in effect), `sh -c '...'`, `eval` and `\git`.
- The session-start hook says that the verify gate is inactive when `cw` is not on `PATH`.
- `TestRunningChecksRetainEveryTerminalSlotAtRevisionLimit` no longer fails intermittently under `-race`: the check-barrier helpers wait for the test's own lifetime instead of a fixed 15-second accept deadline, and report a check that exits before its barrier instead of timing out.
- `cw metrics import --composition` on a transcript with a 500 KB Bash command of quoted `a<<b` words runs about 4.5 times faster under `-race` and 2 times faster without it. Heredoc markers are now matched only at a `<<` outside quotes. Before, a regular expression found every `<<` that has a marker's shape, and the quoted ones were then discarded. A line that has a marker-shaped `<<` but starts no heredoc (for example a quoted one) is also scanned for quotes once instead of up to twice; a line with no `<<` was already scanned once. Results are unchanged. `TestMetricsCompositionStalePhaseLongCommandLinear` no longer fails on loaded `-race` runners ("import took 17.4s, want under 10s"). Its wall-clock bound is removed. Instead, `TestSplitShellWorkLinear` checks that the splitter's quote-scanning and redirect-search work stays linear in the command length.
- `cw metrics import --composition` no longer slows down quadratically on a Bash command with deeply nested unquoted `(`, `$(` or `$((`. The splitter copied its quote-nesting stack for every line and searched it for every heredoc marker, so 20,000 open parentheses followed by 20,000 lines or `a<<b` markers took 45–115 ms to split, and a million would take several minutes, which Ctrl-C could not stop. Copies now share the stack, and each frame records how many arithmetic (`$((` or `((`) frames lie at or below it, so both steps take constant time; the same input now splits in about 5–13 ms. Results are unchanged. The splitter's work count now also includes the stack frames a step copies or searches, and `TestSplitShellWorkLinear` covers deeply nested commands.
