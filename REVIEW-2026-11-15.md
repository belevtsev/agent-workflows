# Agent Workflows code review and developer usefulness report

**Review date:** 15 November 2026. **Repository:** [belevtsev/agent-workflows](https://github.com/belevtsev/agent-workflows). **Reviewed revision:** [c557832010a1eebc3d9cd3bf9f04941855da031f](https://github.com/belevtsev/agent-workflows/commit/c557832010a1eebc3d9cd3bf9f04941855da031f), which matched local and GitHub `main` when inspected.

**Verdict: `cw` has a credible use case as a small local check-evidence gate. The full seven-role workflow is an experiment whose benefits have not been demonstrated, and its existing small-task results argue against making it the default.** The best next investment is to fix the concrete defects below, qualify the host integrations, and measure gate-only use in real repositories.

The implementation contains considerably more engineering than a bundle of agent prompts: it models Git content, records actual command outcomes, handles interrupted processes and damaged records, and checks the content being committed or pushed. It nevertheless needs a sharper product identity. Developers should be able to adopt the gate without adopting a specification methodology, a role hierarchy, or a new usage-reporting tool.

Three reproducible P2 findings are detailed below. No P0 or P1 issue was substantiated in this review. Passing tests establish useful implementation evidence; they do not establish improved developer productivity or complete correctness.

| Part | Assessment | Adoption recommendation |
| --- | --- | --- |
| Check-evidence gate | Useful mechanism with a plausible niche; one confirmed snapshot defect | Pilot after the snapshot fix, alongside existing CI |
| Role workflow and change records | Thoughtful separation of responsibilities, substantial ceremony, two confirmed consistency defects | Keep optional and experimental; use selectively |
| Task and role token reporting | Useful diagnostics with internal-format dependencies | Use for investigation, with explicit unknowns; do not treat totals as ROI or billing |

## What the tool actually provides

The gate separates **running a check** from **deciding whether existing evidence is sufficient**:

1. `cw.toml` declares commands and optionally the paths they depend on.
2. `cw run` snapshots the working tree, executes checks that need fresh evidence, and records their outcomes. A zero exit status counts as passing only if the final snapshot equals the initial snapshot.
3. Git hooks inspect the proposed commit/index tree or relevant pushed tip and consult the records. They do not run the checks themselves.
4. Changed checked content, changed command declarations, failures, missing evidence, expired evidence, or unreadable records can prevent a commit or push.

Without `paths`, a check depends on the entire Git tree. With `paths`, its key hashes matching tree entries, including their modes and object IDs, plus submodule entries. The check identity also compares its declared command and path list. This is content-based reuse, subject to the inputs the repository chose to declare. [Evidence implementation](https://github.com/belevtsev/agent-workflows/blob/c557832010a1eebc3d9cd3bf9f04941855da031f/internal/evidence/evidence.go), [evidence contract](https://github.com/belevtsev/agent-workflows/blob/c557832010a1eebc3d9cd3bf9f04941855da031f/docs/evidence.md).

The role workflow is different. `cw` supplies instructions and validates the files the agents leave behind; the host/model starts the roles and follows the sequence. It does not mechanically execute the workflow, authenticate human approvals, or prove that a named test checks a requirement. Role write limits are checked after the role has acted. That distinction is already stated clearly in the [workflow documentation](https://github.com/belevtsev/agent-workflows/blob/c557832010a1eebc3d9cd3bf9f04941855da031f/docs/workflow.md#the-task-workflow) and should remain prominent in the product description.

The plugin adds session context, a guard against recognizable bypass/edit operations, and notices used to collect host token records. The Git gate works independently of that plugin. A plugin installation alone does not demonstrate that the host has loaded and trusted its hooks.

## Implementation quality

The architecture is reasonably small and understandable. `decl` parses configuration; `gitx` identifies content; `runner` and `proc` execute commands; `store` persists outcomes; `evidence` decides whether they count; `gate` handles Git operations; and `cli` exposes those operations. Roles, change records, and token reporting live in separate packages. There are only two direct module dependencies. [Module](https://github.com/belevtsev/agent-workflows/blob/c557832010a1eebc3d9cd3bf9f04941855da031f/go.mod).

The reviewed tree contains 54 production Go files with 9,426 lines and 151 Go test files with 23,805 lines, counting blank/comment lines. Those numbers describe implementation size, not quality scores. The strongest evidence is the behavior exercised by the tests and the explicit treatment of failure states.

**The strongest engineering choices are:**

- **Commit and working-tree content are distinguished.** A test of unstaged work is not automatically accepted as evidence for a different partially staged commit. Push handling considers the relevant refs rather than assuming the current checkout represents everything being sent. [Gate decisions](https://github.com/belevtsev/agent-workflows/blob/c557832010a1eebc3d9cd3bf9f04941855da031f/internal/gate/judge.go).
- **A successful command is checked against source changes.** Generators, formatters, or concurrent edits that leave different content produce `source_changed`, rather than a misleading pass. [Runner](https://github.com/belevtsev/agent-workflows/blob/c557832010a1eebc3d9cd3bf9f04941855da031f/internal/runner/runner.go#L108-L154).
- **Evidence ordering and corruption are considered.** A sequence number orders completed runs; a later decisive failure does not disappear behind an earlier pass. Damaged, future-dated, and expired records are handled explicitly. [Evidence selection](https://github.com/belevtsev/agent-workflows/blob/c557832010a1eebc3d9cd3bf9f04941855da031f/internal/evidence/evidence.go), [run store](https://github.com/belevtsev/agent-workflows/blob/c557832010a1eebc3d9cd3bf9f04941855da031f/internal/store/runs.go).
- **Process and storage lifecycles are substantial implementations.** Commands use argument arrays; cancellation and descendant cleanup have platform-specific support; captured logs are bounded. Records use temporary files, syncing, rename, and private permissions. [Process execution](https://github.com/belevtsev/agent-workflows/blob/c557832010a1eebc3d9cd3bf9f04941855da031f/internal/proc/proc.go), [storage](https://github.com/belevtsev/agent-workflows/blob/c557832010a1eebc3d9cd3bf9f04941855da031f/internal/store/store.go#L88-L115).
- **Documentation is unusually candid.** The project distinguishes measured behavior, untested host integrations, and hypotheses. It includes executable examples and scenarios for awkward Git behavior. These are useful foundations for maintaining a developer tool.

There is one maintenance policy worth changing: the gate is exactly at its enforced 6,000-line ceiling, while the role portion occupies 3,426 of its 3,500-line allowance. The [size test](https://github.com/belevtsev/agent-workflows/blob/c557832010a1eebc3d9cd3bf9f04941855da031f/internal/repocheck/size_test.go#L11-L16) can keep scope visible, but a hard line-count limit should not force compressed code or defer a clear error message or correctness fix. Prefer architectural boundaries and reviewed complexity budgets over treating every additional source line as a failure.

## Confirmed code and workflow findings

P2 here means a real correctness or workflow defect that should be fixed in normal development before broader adoption. It does not mean a critical security vulnerability. Exact runnable reproductions are in [the appendix](REVIEW-2026-11-15-REPRODUCTIONS.md).

### F1 — P2 — Marked-file checks do not preserve Git type and mode semantics

**Location:** [internal/gitx/snapshot.go, lines 199–210](https://github.com/belevtsev/agent-workflows/blob/c557832010a1eebc3d9cd3bf9f04941855da031f/internal/gitx/snapshot.go#L199-L210).

`Snapshot` uses a copied index and `git add -A`. It then explicitly examines files marked `assume-unchanged` or `skip-worktree`, since Git can overlook changes to those paths. However, `checkMarked` compares only `git hash-object <path>` with the indexed object ID. It does not compare file mode/type, and that command follows a symlink instead of hashing the stored link text.

**False pass:** on Linux with `core.filemode=true`, commit a non-executable `check.sh`, declare `run = ["./check.sh"]`, mark the file assume-unchanged, and make the working copy executable. `cw run` records a pass and `cw hook pre-commit` allows the index tree, even though that tree still stores mode `100644`. Running the same declared check in a fresh clone of that committed content fails with permission denied. The same result was reproduced with `skip-worktree`.

**False rejection:** commit an ordinary symlink, mark it with either flag, and change nothing. `cw run` rejects it as differing from the index because the target bytes and link text hash differently. Both manifestations were reproduced for both mark types.

This violates a concrete content property that Git records; it is separate from the documented exclusion of environment variables and compiler versions. It is uncommon because it requires marked files, but it weakens the central evidence promise.

**Suggested fix:** compare file kind and executable mode using Git's configured semantics and handle symlink text correctly. Alternatively, use another disposable index with the marks cleared and compare the resulting entries. Preserve legitimate `core.filemode=false` and `core.symlinks=false` behavior. Add targeted cases for executable-only changes, unchanged/changed symlinks, and regular-file/symlink transitions under both flags.

### F2 — P2 — The post-shipping procedure asks the spec-writer to violate its own permissions

**Locations:** [role limit](https://github.com/belevtsev/agent-workflows/blob/c557832010a1eebc3d9cd3bf9f04941855da031f/internal/roles/roles.go#L173-L179), [post-shipping instructions](https://github.com/belevtsev/agent-workflows/blob/c557832010a1eebc3d9cd3bf9f04941855da031f/internal/roles/text/coordinator.md#L224-L230), and the [spec-writer instructions](https://github.com/belevtsev/agent-workflows/blob/c557832010a1eebc3d9cd3bf9f04941855da031f/internal/roles/text/spec-writer.md).

After a finished change ships, the coordinator is instructed to start `spec-writer` to update `openspec/specs/`. That role is allowed to modify only the selected change folder's `proposal.md` and `specs/`. Its write checker therefore rejects the prescribed update.

An isolated addition of `openspec/specs/greeting/spec.md`, followed by `cw roles check spec-writer --from HEAD --task add-greeting`, exits 5 and tells the coordinator to start the role again without accepting its work. No available permission mode resolves that conflict. The coordinator's statement that shipping is outside the normal paths does not change the role's unconditional limit or the general requirement to check each role.

This affects synchronization and archival after shipping; it does not block every ordinary task from reaching completion.

**Suggested fix:** define a narrow finalization operation or permission mode, or assign synchronization to an explicitly authorized coordinator operation. Align the role text, checker, coordinator, and workflow documentation. Add an end-to-end shipped-change test; do not simply allow every spec-writer invocation to edit all living specifications.

### F3 — P2 — Duplicate scenario titles conceal missing test mappings

**Locations:** [name-only lookup](https://github.com/belevtsev/agent-workflows/blob/c557832010a1eebc3d9cd3bf9f04941855da031f/internal/change/folder.go#L467-L476), [mapping validation](https://github.com/belevtsev/agent-workflows/blob/c557832010a1eebc3d9cd3bf9f04941855da031f/internal/change/rules.go#L196-L205).

The checker finds a scenario's test row by display name alone. Different requirements or capabilities can both have a scenario named `Happy path`, `Invalid input`, or `Unauthorized request`. One matching row then satisfies both. No validation requires those names to be globally unique.

The reproduction has separate Greeting and Authorization requirements, both containing `Happy path`. Its sole row names a greeting test; there is no authorization mapping. With the remaining design, review, approval, and commit records in place, `cw change check` exits 0 and `cw change status` reports `done`.

This is a structural identity problem, not a demand that the tool understand test semantics. The [declared contract](https://github.com/belevtsev/agent-workflows/blob/c557832010a1eebc3d9cd3bf9f04941855da031f/openspec/changes/add-role-workflow/specs/change-record/spec.md#L125-L127) requires one row per scenario; the implementation cannot distinguish these two scenarios.

**Suggested fix:** use a qualified identity such as capability + requirement + scenario, or stable scenario IDs. An interim fix can reject ambiguous duplicate names with an actionable message. Cover both rule checking and stage calculation in the regression.

## Trust limits that affect usefulness

These are mostly intentional boundaries, not additional undiscovered defects. They determine where adoption is sensible. [Security policy](https://github.com/belevtsev/agent-workflows/blob/c557832010a1eebc3d9cd3bf9f04941855da031f/SECURITY.md), [evidence contract](https://github.com/belevtsev/agent-workflows/blob/c557832010a1eebc3d9cd3bf9f04941855da031f/docs/evidence.md), [hook behavior](https://github.com/belevtsev/agent-workflows/blob/c557832010a1eebc3d9cd3bf9f04941855da031f/docs/hooks.md).

| Boundary | Practical consequence |
| --- | --- |
| The user/agent can write hooks, records, and configuration | This prevents cooperative mistakes; it is not tamper-proof enforcement |
| `paths` is a manually declared dependency set | Missing a lockfile, configuration file, fixture, or script can reuse a pass after a relevant change |
| Tool versions, environment, ignored files, external services, and symlink target contents are outside the snapshot promise | Same Git content does not imply the same execution environment |
| Only before/after snapshots are compared | A transient edit that is restored during a run is not observed |
| Separate clones and CI do not share evidence | This is not a distributed build cache or portable attestation system |
| `cw run --base` assumes unchanged checks on the named base passed | Use a genuinely trusted base; the flag does not obtain an independent proof of its success |
| A changed or removed check changes the policy itself | CI using the changed declaration cannot detect every weakening; independent review of policy matters |
| Shared hooks need correct ordering, exit propagation, and preserved pre-push stdin | Integration with another hook manager needs functional tests, not just a matching line in a file |
| `cw change` checks records and references | `done` is not a semantic proof that the implementation satisfies the user's intent |

`cw run` deliberately returns success when a selected subset passes even if other checks remain missing. Scripts that need the overall verdict should inspect the full state rather than equating every successful partial run with verification. Likewise, an empty check declaration explicitly permits commits; setup completion is not evidence that a repository has meaningful tests.

The gate should continue to make a precise statement: a declared command succeeded for specified Git content under local conditions. Required CI and review should remain the authority for shared branches. Stronger security attestations, remote trust, or hermetic execution would be a materially different product.

## Evidence for developer value

### Independent measurement of hook cost

The current performance harness was run separately from the race suite, using 15 decisions after one warm-up for each case:

| Fixture | Median hook decision | Observed range | Harness limit |
| --- | ---: | ---: | ---: |
| Copy of the reviewed repository, 306 files, 2.5 MiB | 34.5 ms | 33.8–35.8 ms | 150 ms |
| Generated repository, 30,000 files, 68 MiB | 24.1 ms | 23.7–25.1 ms | 500 ms |

The decision itself is inexpensive in these two local cases. The larger fixture being faster does not establish inverse scaling: the fixtures differ, their caches differ, and this is not a controlled scaling experiment. These measurements exclude the cost of running the actual checks, repeated working-tree snapshots, and a developer recovering from a denial. They also say nothing about p95 behavior on Windows, network filesystems, or real monorepos.

The repository's earlier size experiment reports about one second for `cw run` with one trivial check at 100,000 generated files, on a memory filesystem. That is useful context for cheap checks: the snapshot work can dominate the command itself. [Published benchmark setup and results](https://github.com/belevtsev/agent-workflows/blob/c557832010a1eebc3d9cd3bf9f04941855da031f/docs/benchmarks.md).

| Task and arm | Reported cost | Session time | Role starts | Hidden acceptance tests |
| --- | ---: | ---: | ---: | --- |
| Duration parser, plain agent | $0.17 | 27 s | 0 | Pass |
| Duration parser, gate | $0.16 | 23 s | 0 | Pass |
| Duration parser, full roles | $9.84 | 42 min | 16 | Pass |
| Slug defect, plain agent | $0.15 | 24 s | 0 | Pass |

From the displayed rounded figures, full roles cost about 58 times as much for the duration task and took about 93 times as long. The requested small role workflow cost about 4.8 times as much for the slug defect. Those are arithmetic descriptions of individual trials, not predictions of typical overhead. The document's narrative ratios differ slightly; these calculations use only its displayed numbers.

All these variants passed the supplied hidden tests, so the extra work has no demonstrated acceptance-score benefit in this sample. That does not prove equal maintainability or equal performance on complex changes. It does make a default seven-role prescription difficult to justify.

Several details matter more than the headline ratios:

- The full duration workflow produced 55 lines of implementation, 62 tests in 315 lines, and 1,023 lines of change records. The plain agent produced 27 implementation lines and five tests in 43 lines. Volume is not a quality metric.
- A script approved every clarification with a fixed response. Human reading, deliberation, and interruption time are absent from the measurements.
- The role solution used `TypeError` for non-text input after proposing that change, while the request specified `ValueError`. The hidden suite only checked strings. This exposes an acceptance-test blind spot; the blanket approval also makes it unsuitable as a clean example of unauthorized behavior.
- The coordinator ran the mandated role check after 15 of 20 starts and omitted it after five reviewer starts. Instructions alone did not deliver complete protocol compliance even in the small sample.
- For the tiny slug fix, an ordinary request to use the workflow led the coordinator to recommend the direct path and start no roles. Keeping that escape path is a good choice.

Small gate/plain cost differences do not establish savings. The planned broader evaluation remains unrun. The evidence currently supports feasibility and identifies overhead; it does not establish less human work, fewer escaped defects, or higher-quality accepted changes.

### Token attribution is diagnostic rather than economic proof

Reading host records instead of accepting an agent's token estimate is a strong choice. The implementation handles Claude message deduplication and Codex cumulative counters separately, updates repeated notices, and distinguishes unknown data from zero. Task/stage labels can make a costly workflow easier to inspect. [Token implementation](https://github.com/belevtsev/agent-workflows/blob/c557832010a1eebc3d9cd3bf9f04941855da031f/internal/tokens/read.go), [token contract and validation](https://github.com/belevtsev/agent-workflows/blob/c557832010a1eebc3d9cd3bf9f04941855da031f/docs/tokens.md).

However, input, cached input, output, and different models do not have equal economic cost. The “workflow” share includes activity a single agent would also do, and later writing rounds are categorized as rework even when they are planned phases. Prompt labels can be wrong; internal host formats can change; a final turn can be missing when a hook fires before the transcript is flushed. The tool itself reports token counts, not dollars. None of these totals alone establishes whether a role earned its cost.

### The comparisons that most affect the product decision

**Existing hooks are the practical baseline.** A team with fast, reliable pre-commit checks may gain little from another manifest and an explicit run command. The strongest demonstration would involve a check that already passed, a subsequent edit or partial staging, and a correct explanation of whether that evidence still applies. Measure the whole loop, including retries, rather than comparing hook startup alone.

**Trunk and polylint narrow the caching argument.** Their documented precomputation, staged snapshots, and version/configuration-aware reuse mean “cached checks for agents” is too broad a differentiator. `cw` can instead wrap arbitrary existing tests/builds and provide one understandable receipt model. Optional explicit environment fingerprints may be useful later, but first collect examples where the current content-only model misleads users. [Trunk](https://github.com/trunk-io/docs/blob/main/code-quality/overview/README.md), [polylint](https://github.com/Goldziher/polylint/blob/main/README.md).

**Spec Kit and Superpowers raise the workflow standard.** They already offer explicit processes and lighter execution options. `cw`'s file validators and role-change checks are interesting, but a comparison should ask whether they reduce defects or human review time at equal task/model budgets. Their mere existence does not prove better results for any of these tools. [Spec Kit workflows](https://github.github.io/spec-kit/workflows/overview.html), [Superpowers](https://github.com/obra/superpowers/blob/main/README.md).

**Native host support is both a dependency and a substitute.** Host-specific hooks and agents can cover simpler cases directly. Codex's hook trust requirement also makes “installed” distinct from “operational.” A compatibility check and real-host trial are more valuable near-term than adding another role. [Codex hooks](https://learn.chatgpt.com/docs/hooks), [Claude subagents](https://code.claude.com/docs/en/sub-agents).

**Token attribution should support decisions.** Generic token and cost dashboards are already available. The useful extension is an outcome-linked record: which role used resources, what defect it caught, how much human time it required, and whether the final change passed acceptance. Preserve known/unknown distinctions and pricing assumptions. [ccusage guide](https://ccusage.com/guide/).

This search is broad enough to identify close substitutes, but it is not an exhaustive survey of proprietary tools or internal company systems. The recommended positioning is an inference from those comparisons, not customer validation.

## What broader research supports

The wider research supports testing this idea, not assuming it works:

- **Multiple agents help some task structures and hurt others.** Google's January 2026 report studied 180 configurations and found that parallelizable versus sequential work strongly affected results. Its four benchmark domains were not a direct trial of `cw` or this seven-role coding process. The practical implication is to evaluate role splits by task type. [Google Research](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/).
- **Research-agent success does not transfer automatically to coding.** Anthropic describes gains on its internal research evaluation, substantial token consumption, and fewer naturally parallelizable subtasks in much coding work. That supports parallel investigation and independent review as hypotheses; it does not validate long serial role handoffs. [Anthropic engineering report](https://www.anthropic.com/engineering/multi-agent-research-system).
- **Tests can be gamed.** ImpossibleBench studies deliberately conflicting specification/test situations and shows why a passing test result can reflect an inappropriate shortcut. Independent test ownership is a sensible response to one failure class, but unchanged tests still do not prove adequate coverage or correct intent. Its deliberately impossible tasks should not be treated as a measured everyday cheating rate. [ImpossibleBench paper](https://arxiv.org/abs/2510.20270).
- **Productivity measurement is difficult and changes over time.** METR's February 2026 update reports selection and timing problems in its follow-up experiment and cautions that the data are a weak signal of current speedup. Quoting the earlier 2025 slowdown as a general current verdict would be misleading. `cw` should measure its own users and include human effort, task selection, and concurrent-agent work. [METR update](https://metr.org/blog/2026-02-24-uplift-update/).

Historical Aider results provide a narrower positive example: an architect/editor combination achieved 85.0% versus a 79.7% o1-preview baseline in the maintainers' September 2024 code-editing benchmark. It demonstrates a particular role split and model pairing, not a general seven-role advantage. [Aider experiment](https://aider.chat/2024/09/26/architect.html).

| Team with long checks that are often rerun on unchanged content | Potentially useful | Receipt reuse may save time; compare against existing command/build caches |

A clearer opening message would be: **“Keep a receipt of the checks that passed for the code you are about to commit.”** Follow it with a short demonstration of test → edit → denied commit → rerun → allowed commit, then explain partial staging. Update the repository's older “personal Codex skills / macOS/Linux” description to match the current cross-platform gate.

Keep the release scope modest. Remote attestations, a new orchestration runtime, a large plugin marketplace, and comprehensive billing analytics each create a separate maintenance burden. They should follow evidence of demand rather than precede a successful gate pilot.

## Evaluation that would answer whether it helps developers

Two separate hypotheses need testing: **the gate prevents stale-check mistakes at acceptable friction**, and **additional roles improve accepted work enough to pay for their cost**.

**First test gate mechanics against a practical baseline.** Use no local gate, a conventional check-running hook, and `cw`, with identical checks. Inject edits after a pass, partial staging, changed check configuration, branch/rebase changes, linked worktrees, absent installation, and a flaky failure followed by a pass. Count correct blocks, false blocks, recovery time, repeated execution time, and p50/p95 latency. An ordinary hook that reruns the checks may already solve many cases; include its full cost fairly.

**Then run a bounded real-task comparison.** A useful pilot could use 18 tasks across three existing repositories, four arms, and three repeats: 216 sessions. That is a proposed study size, not a statistical power guarantee or authorization to spend model credits. Include small defects, new behavior, refactoring, and cross-module changes.

| Arm | Configuration | Question answered |
| --- | --- | --- |
| A | Capable single agent, ordinary repository instructions/checks/CI | Practical baseline |
| B | A plus the `cw` gate and small skill | Incremental value of the gate |
| C | B plus one independent reviewer | Whether a small role split captures most of the benefit |
| D | Full `cw` role workflow | Incremental value of the full methodology |

Hold model/effort, repository state, test suite, and tool versions constant for the primary comparison; randomize execution order. If production roles intentionally use different models, report that as a separate cost-optimized experiment. Use the same clarification answers in every arm and count the human time needed to supply them. Blind the final code reviewers to the arm where practical.

Acceptance tests should be hidden from the agents, include errors and boundary cases, and check the actual request rather than just the generated spec. Add independent review of maintainability, unnecessary edits, test weakening, and escaped regressions. For every arm, record time to first accepted commit, human minutes, token categories/model costs, failed attempts, interventions, and missing token data. Publish exact versions and raw results with appropriately sanitized artifacts.

For adoption, label each denial: genuinely stale/missing evidence, configuration mistake, environmental problem, or false refusal. A denial is not automatically a prevented bug. Measure whether developers continue using the tool voluntarily after the pilot, and why they bypass or remove it.

Agree on decision criteria before running. Retain a role if it reduces defects or human review/rework enough to justify its added elapsed time and spend. Keep the gate if it catches a relevant failure class with acceptable setup and recovery cost. Define latency and false-refusal tolerances for the intended teams and machines; this review does not supply universal thresholds.

The existing [evaluation plan](https://github.com/belevtsev/agent-workflows/blob/c557832010a1eebc3d9cd3bf9f04941855da031f/docs/evaluation.md) provides a useful starting point. Separating gate-only, reviewer-only, and full-role arms would make its results substantially more actionable.
